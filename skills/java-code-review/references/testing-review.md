# 测试审查参考

当审查行为变更是否具备足够测试时使用本参考。

## 按变更类型判断测试期望

| 变更类型 | 应关注的测试 |
| --- | --- |
| Controller/API | 成功、参数校验失败、鉴权失败、错误映射、响应兼容性。 |
| Service 业务规则 | 正常路径、边界条件、空值、非法状态、重复请求。 |
| Mapper/XML SQL | 动态 SQL 分支、分页、空结果、索引相关条件、写入数量。 |
| 事务 | 失败回滚、局部写入防护、重试行为。 |
| MQ 消费者 | 合法 payload、重复 payload、非法 payload、下游失败、重试/死信行为。 |
| MQ 生产者 | 消息内容、topic/tag/group、发布失败处理、DB 一致性。 |
| Redis/缓存 | key 格式、TTL、命中/未命中、失效、脏数据防护。 |
| 分布式锁 | 加锁失败、超时、owner token 安全释放。 |
| 外部客户端 | 超时、提供方错误映射、fallback/降级、敏感日志。 |
| 安全/签名 | 非法签名、过期时间戳、重放编号、未授权资源访问。 |

## 审查指引

- 只有行为发生变化或风险有实际意义时，缺少测试才作为 Finding。
- 优先给出具体建议测试，不要只写“增加测试”。
- 如果基础设施不可用导致测试无法运行，说明阻塞原因，并指出最接近的可行验证方式。
