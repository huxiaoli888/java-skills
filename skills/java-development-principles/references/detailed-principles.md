# Java 开发原则详细规则

本文件承载 `java-development-principles` 的低频细则。主 `SKILL.md` 只保留触发、核心红线、执行清单和路由；需要深入判断 SOLID、事务、异常、日志或测试策略时再读取本文件。

## SOLID 指导

### 单一职责

当一个文件同时处理下列两项或更多事项时应拆分：

- 请求解析
- 授权决策
- 业务规则
- 持久化
- 远程 API 调用
- 响应格式化
- 事件发布
- 定时任务协调

### 开放封闭

新增业务类型、渠道、策略、供应商或规则时：

1. 查找已有接口、handler、策略、factory、枚举 registry 或配置。
2. 若不存在且该变化可能重复出现，创建最小扩展点。
3. 尽量以新的类或模块实现新行为。
4. 避免在核心流程中扩大 `if/else` 或 `switch`。

简单的一次性决策可使用分支；持续增长的业务变体应使用多态、策略或 registry。

### 依赖倒置

- Service 应依赖外部系统及可替换策略的接口。
- 基础设施实现应隐藏在 client、gateway、repository 或 adapter 后。
- Controller 不得直接实例化具体 client、repository 或工具。

### 接口隔离

- 接口应聚焦于一个客户端需要或一个内聚能力。
- 不要让实现依赖其不使用的方法。
- 当不同调用方需要无关操作时，拆分宽泛的 service、client、mapper 或 strategy 接口。
- 优先采用角色专用端口，例如 `OrderReader`、`OrderWriter`、`PaymentVerifier` 或 `CredentialAuthenticator`，而非一个过大的 manager 接口。
- 若接口只因单个类有一个实现而存在，且没有现实的替换点，在其不能澄清真实边界或测试缝隙前不要新增。

### 组合复用

- 优先组合小型 service、策略、校验器、handler 和 adapter，而不是继承大型基类。
- 继承主要用于框架要求、稳定的领域层次，或真正表达 “is-a” 关系的共享契约。
- 不要把可变业务流程、远程调用、事务决策或请求专属状态放在抽象基类中。
- 跨功能复用行为时，先考虑协作组件、最小钩子的模板方法、策略，或仅用于纯无状态函数的工具。
- 避免令未来变体必须覆盖无关方法或依赖父类副作用的继承。

## 事务规则

- 将 `@Transactional` 放在 service/use-case 层，不要放在 controller。
- 在正确性允许的前提下保持事务范围尽可能小。
- 除非必要且已记录，不要在数据库事务中执行缓慢的远程调用。
- 对多步骤写操作明确回滚行为。
- 对可重试操作考虑幂等键或重复请求保护。
- 当数据库写入与 MQ 消息必须保持一致时，记录所选模式：事务 outbox、本地消息表、提交后发布、补偿任务或项目专用框架。
- 不要把分布式一致性要求隐藏在工具类中。

## 异常规则

- 使用全局异常处理器进行 API 错误映射。
- 仅在补充业务上下文、有意恢复或将外部错误转换为领域/应用错误时捕获异常。
- 不要吞掉异常。
- 不要在多层重复记录同一异常的堆栈。
- 保持错误码稳定且具有业务含义。

## 日志规则

- 记录一条包含 trace id、方法、路径、状态和耗时的请求摘要。
- 对手机号、令牌、凭据、证件号和其他敏感字段脱敏。
- 记录工具或外部调用边界的 `reqid` 和结果状态，不记录完整敏感载荷。
- 日志应有助于定位生产问题，同时不得泄露私密数据。

## 常见反模式

| 反模式 | 修正方式 |
| --- | --- |
| Controller 查询数据库、调用外部 API 并组装业务状态。 | 将编排移至 service；controller 只负责校验和 HTTP 适配。 |
| Service 构建 SQL 字符串或了解 mapper XML 细节。 | 将 SQL 移至 mapper/repository，让 service 保持业务意图。 |
| DTO 同时作为 entity、MQ 载荷和外部 API 对象。 | 当生命周期或兼容性要求不同时拆分契约。 |
| `utils` 类读取 Redis、DB、MQ 或配置并作出业务决策。 | 重命名并移至 service、adapter、gateway 或策略组件。 |
| 面向业务类型的大型 `if/else` 持续增长。 | 当变体重复出现时引入策略、handler map、registry 或多态。 |
| 捕获 `Exception` 后返回成功或默认值。 | 让全局处理映射错误，或转换为有意义的业务异常。 |
| 记录完整请求/响应体。 | 只记录标识、状态、耗时及脱敏字段。 |

## 审查清单

审查 Java 改动时，检查：

- controller 中的业务逻辑。
- 本应属于 mapper/repository 的 service SQL 或持久化细节。
- DTO/entity 跨层泄露。
- 请求 DTO 缺失校验。
- 事务边界缺失或不正确。
- 围绕远程调用的宽泛事务。
- 持续增长的 `if/else` 或 `switch` 变体逻辑。
- 被吞掉的异常。
- 不一致的错误码。
- 日志中的敏感数据。
- 改动行为缺少测试。

## 测试策略

选择能验证改动行为的最小测试：

| 改动类型 | 建议测试 |
| --- | --- |
| Controller 请求/响应、校验、错误映射 | 遵循项目既有风格的 `MockMvc` 或 `WebTestClient`。 |
| Service 业务规则 | JUnit + Mockito 或项目认可的测试替身风格。 |
| Mapper 或 repository SQL | 使用项目测试数据库配置的 mapper 测试、repository 测试或集成测试。 |
| 外部 HTTP client | WireMock/MockWebServer 等 mock server，或既有 client 测试模式。 |
| MQ consumer | 使用代表性载荷以及幂等/重试场景的 listener 测试。 |
| 事务或幂等行为 | 覆盖重复请求、回滚、重试和补偿的边界测试。 |

如果因 DB、MQ、Nacos、Redis 或私有依赖不可用而无法运行测试，说明阻塞因素，并运行最接近的静态或模块级验证。
